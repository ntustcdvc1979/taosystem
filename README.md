# 成全名單管理

多人共用的名單管理網頁，前端部署在 GitHub Pages，資料存在 Firebase（Firestore），登入用 Firebase Authentication 限制只有指定人員能存取。

## 兩個系統：道務／班務

登入後，標題列下方有 **「道務系統 ／ 班務系統」** 兩個分頁，**頁面與資料都不共用**（只有上面的標題列、使用者管理是共用的）。切到哪一邊會依帳號記在這台裝置上，下次登入回到同一邊。

| | 道務系統 | 班務系統 |
|---|---|---|
| 名單 | 成全對象（團隊／個人名單） | **班員／護班人員**（可同時在好幾個班） |
| 活動 | 活動管理（廣結善緣、法會…） | **課程管理** |
| 紀錄 | 活動紀錄、聯絡紀錄 | **上課紀錄、佛規禮節、經典背誦** |
| 指標 | 熱度、參與度、互動度、道氣、趨勢分析 | （無，班務看的是出席與學習狀況） |
| 集合 | `entries`／`personalEntries`／`events` | `classEntries`／`courses` |

AI 成全助手只在道務系統出現——它讀的是成全名單。

**兩個系統各自授權**：帳號要有道務身分才進得了道務系統，要有班務身分才進得了班務系統。沒被授權的那一邊，分頁會顯示成「道務系統（未授權）」，點下去只會告訴你沒有權限，不會切過去；兩邊都沒授權的帳號連登入都會被擋下來。詳見「[身分（班務組長）](#身分班務組長)」。

詳細用法見下面的「[班務系統](#班務系統)」一節。

## 道務單位與帳號

每支帳號都屬於一個**道務單位**，資料按單位隔離：**不同單位彼此看不到對方的名單、活動與對話**。單位由管理員在 Firebase Console 指派，網頁上只顯示（在帳號 Email 旁邊）而不提供修改。

資料放在 `units/{unitId}/…` 底下（entries／personalEntries／events／chatHistories），**用路徑而不是欄位來隔離**——Firestore 的安全規則無法過濾查詢結果，若用欄位區分，查詢範圍一旦含有讀不到的文件，整個查詢就會被拒絕；用路徑則查詢天然只看得到自己單位的資料。

### 管理員設定（在 Firebase Console 做）

1. 建立單位：`units/{unitId}` 文件，欄位 `name` 填單位名稱（例如「台科崇德」）。`unitId` 自訂（例如 `ntust-chongde`）。
2. 指派帳號：`memberEmails/{對方的 gmail（小寫）}` 文件，欄位 `unitId` 填上面的單位 ID。
   - 同一份文件的 `roleRank` 決定**道務身分**（4 點傳師／3 忠義字班講師／2 成全組長／1 組員／**0 或沒寫＝未授權**）；
     `classRank` 決定**班務身分**（4 點傳師／3 忠義字班講師／2 班務組長／1 班務人員／**0 或沒寫＝未授權**）。
     兩者分開，**兩個都是 0 的帳號登不進來**，見「[班務系統](#身分班務組長)」。
   - **第一位講師或點傳師要在這裡設定**；之後增減使用者、調整身分都可以直接在網頁上做。
   - **沒有這份文件的帳號一律進不去**，這取代了舊版寫在安全規則裡的 Email 白名單。
3. `units` 只能從 Console 修改；`memberEmails` 只有該單位的忠義字班講師以上改得動。

### 帳號綁定（每位使用者自己做一次）

每位幹部自己也是名單中的一員。登入後若尚未綁定，右上角會出現「**綁定我的資料**」按鈕，點開搜尋自己的名字即可。若名單上還沒有自己，視窗會提示先用「＋ 新增名單」把自己加進團隊名單再回來綁定。

綁定後系統才知道名單上哪一位是你——個人名單的聯絡人會自動帶入你的名字。綁定關係存在 `units/{unitId}/memberLinks/{uid}`，只能設定自己那一份。

**綁錯了要改**：那顆按鈕綁好之後不會消失，只會變成「**重新綁定**」，點開再選一位就直接覆蓋（`memberLinks` 一個帳號就一份）；視窗裡也會顯示「目前綁定：某某」與一顆「**解除綁定**」。

**幫別人綁**：成全組長以上可以在「使用者管理」裡，對每個帳號按「**指定綁定**」直接指定他是名單上的誰——對方**還沒登入過也設得起來**（寫在他的 `memberEmails/{gmail}.entryId`，因為那時候還沒有 uid 可以寫 `memberLinks`）。已經指定過的按鈕會顯示「綁定：某某」。

自己綁的與被指定的兩者**以比較新的為準**（各自帶時間戳），所以組長改得動、當事人之後也還是可以自己重綁。

「使用者管理」上顯示的是**實際生效的那一筆**——它同時看 `memberLinks`（自己綁的）與 `memberEmails.entryId`（被指定的），所以某個人自己綁好之後，這裡也會立刻顯示成「綁定：某某」，不會還停在「指定綁定」。

## 欄位

歸屬（團隊名單／個人名單）、姓名、性別（乾／坤，坤以紅色標示）、系級、標籤（可多個）、背景、聯絡人、成全狀況（固定選項：未求道／已求道／法會畢／新民班畢／至善班畢／行德班畢／崇德班畢／人才儲訓班畢／講培班畢／講師／未確定）、策略、做法、推薦活動（由 AI 建議產生）。

> **刪除名單要問兩次**：這個動作不可復原、也沒有備份可還原，所以第一關會先告訴你會連同幾筆活動紀錄與聯絡紀錄一起刪掉，第二關要**把那個人的姓名打一次**才會真的刪除。打錯或取消都會中止。
>
> 刪除入口有兩個：卡片上的「刪除」，以及**編輯視窗左下角的「刪除這筆」**（只在編輯既有名單時出現，刻意放在離「儲存」最遠的一側）。兩邊走的是同一套確認，刪成功才會關掉視窗。

### 標籤怎麼打

標籤欄不是純文字：**打字的當下就會搜尋名單上已經用過的標籤**（常用的排前面），點一下或按 Enter 就變成一個圓角標籤，右邊有 × 可以拿掉；輸入框空的時候按 Backspace 會刪掉最後一個。逗號、頓號同樣可以斷開，中文選字中的 Enter 不會誤送出。已經加上的標籤不會再出現在建議清單裡。

> **下拉清單為什麼要這樣寫**（標籤、活動邀約挑人、班務打姓名對應道務名單三處共用 `bindPick`）：
>
> 1. **清單不靠 blur 收起來**，改成「碰到這個欄位以外才收」。手機上手指一按下去輸入框就先失焦，清單若跟著消失，那一下會落在已經不存在的元素上——這才是點不到的主因。
> 2. **pointerdown 與 click 兩個都接**：手機點下去只有 pointerdown／touchstart（沒有 mousedown），而只綁 click 也不保險——中文選字送出等情況會讓清單在按下與放開之間重畫，click 的目標就變成外層容器而落空。pointerdown 先處理，click 兜底（鍵盤與輔助工具只有 click），同一下用旗標擋住，不會一次選到兩個。
> 3. 每一列高度加大到 40px 以上並加上 `touch-action: manipulation`，手指點得準、也不必等瀏覽器判斷是不是要雙擊縮放。

這樣同一個意思就不會被打成好幾種寫法（需關心／要關心／需要關心…）。趨勢分析裡的「加標籤」用的是同一個元件，而且可以一次加好幾個標籤。

名單以**卡片**呈現（依螢幕寬度自動排欄），長文字預設收合 3 行、點一下展開。標籤會顯示為 chip，也可用搜尋框搜到。**在未搜尋、未篩選狀態下可直接拖曳卡片調整順序**，順序會存回資料庫（所有人看到的順序一致）。

### 團隊名單與個人名單

名單分成兩種歸屬，新增時可選（預設是團隊名單）：

- **團隊名單**：同一個道務單位的成員共同管理，彼此都看得到。存在 `units/{unitId}/entries`。
- **個人名單**：**只有建立者本人看得到、改得動**，同單位的其他成員連讀都讀不到（由安全規則限制，不只是畫面隱藏）。存在 `units/{unitId}/personalEntries`，每筆記著 `ownerUid`。個人名單的**聯絡人固定是你自己**，所以表單不會出現聯絡人欄位。

因為別人的個人名單根本不會被讀進來，所以**活動邀約的搜尋不會出現別人的個人名單，AI 也看不到**——這是資料層的保證，不是畫面上的過濾。

卡片上的個人名單會有紫色「個人」標記。工具列的**名單篩選**可切換「全部名單／團隊名單／我的個人名單」。

**轉移**：個人名單的卡片上有「轉為○○名單」按鈕，確認後就變成團隊名單（同單位都看得到）。轉移會沿用同一個文件 ID，所以活動邀約名單裡的紀錄不會失效。**網頁上無法把團隊名單轉回個人**，因為其他人可能已經看過、也可能已經在協助跟進了。

### 兩種檢視模式

工具列的「**切換熱度模式／切換詳細模式**」可切換名單呈現方式：

- **熱度模式**（預設）：一人一張小卡（手機一欄、桌機自動多欄），左側是圓形的熱度徽章，旁邊是成全狀況、參與度與最近互動時間，下方直接有「活動紀錄／聯絡紀錄／熱度／編輯」四個按鈕。
- **詳細模式**：完整卡片，看得到背景、策略、做法、最近紀錄與各種操作按鈕。

#### 參與度

近一個月**活動出席比例**。

分母是近 30 天辦過的活動場次，包含兩個來源：「活動管理」裡登錄的活動，以及**只寫在個人活動紀錄裡、沒登錄到活動管理的活動**（例如臨時的系上聚餐）。以活動名稱辨識，所以同一場活動即使既有登錄又有人寫在活動紀錄裡，也只算一場。

分子是這個人出席的場次：他的活動紀錄裡有這場，或在該活動的邀約名單中回覆「已回覆可以」。

- 高 ≥60%、中 ≥30%、低 >0%、無 0%；近一個月沒有活動時顯示「—」。
- 滑鼠移到徽章上會顯示「近一個月 N 場中出席 M 場」。

#### 互動度

近兩週（14 天）**有幾天跟這個人有互動**，互動包含聯絡紀錄與活動紀錄。以「有互動的天數 ÷ 14」計算：高 ≥4 天（約每週兩次）、中 2–3 天（約每週一次）、低 1 天、無 0 天。

**同一天內補登多筆只算一天**，避免一次補完一整週的紀錄就把分數衝高。滑鼠移到徽章上會顯示「近兩週有 N 天互動」。

#### 成全熱度

熱度代表**從談話內容看，這個人離下一階段有多近**（未求道者的下一階段是求道，已求道者是法會或研究班）。分成 冷／涼／溫／熱 四級，顏色由灰藍→藍→琥珀→紅。

熱度由兩部分組成：

1. **基準值**——由 **AI 依活動紀錄與聯絡紀錄的內容判斷**，例如未求道者聊到求道、已求道者聊到法會且對方有正面回應，就會評為「熱」；只有一般寒暄則是「涼」。也可以**手動設定**。
2. **時間衰減**——每過 **7 天**沒有新的互動，顯示的熱度就**降一級**，提醒你該再關心了。

**什麼算「最近一次互動」**：活動紀錄、聯絡紀錄，**再加上班務系統裡他有到的上課紀錄**。前天在新民班見過面，道務這裡就會顯示「2 天前」、熱度也不會因此掉下去——人明明才見過，卻因為沒人補一筆聯絡紀錄而被判定為久未關心，是不合理的。

- 只認**準時／遲到**（真的到場）；**請假／缺席**那天並沒有見到人，不算互動。
- 要**關聯到道務名單**的班務名單才算得進來（就是打姓名時對應的那一位）。
- 讀得到班務名單才算得進來：**沒有班務權限的帳號**看不到 `classEntries`，他看到的「幾天前」就只算道務那兩種紀錄。
- **參與度與互動度不受影響**，仍然只看道務的活動與聯絡紀錄。

熱度在卡片上的呈現方式：

- **圓圈旁一個三角形**表示跟**一週前**比是升是降：**▲ 紅色＝上升**（例如剛聯絡過，從衰減中回升）、**▼ 藍色＝下降**。滑上去顯示「較一週前上升：冷 → 熱」或「較一週前下降：溫 → 涼（已 9 天沒聯絡）」。沒變化就不顯示三角形。
- 超過 7 天沒互動時，**「N 天前」會標成紅字**（滑上去會說明它同時看活動、聯絡與班務上課紀錄）。
- 卡片下方那行顯示的是**做法**——那才是每天要照著做的事。**熱度的評語（AI 或手動）改放在「熱度」視窗裡**，連同「評估為 X、已 N 天沒聯絡而降為 Y」的完整說明；沒有評語時視窗會提示可以用 AI 產生或手動點選級別。

操作方式：

- **AI 評估熱度**（工具列，僅熱度模式顯示）：一次評估目前看得到的所有人。會先跳出確認（含人數），因為它要把每個人的紀錄都送給 AI、要跑一陣子，而且**已經手動設定過熱度的人也會被覆蓋**。
- **熱度**（每張卡片上）：開啟視窗手動調整級別，或單獨用 AI 重新評估這一位；視窗裡會同時顯示 AI 的評語與衰減情形。

熱度存在對象的 `heat` 欄位（級別、評語、來源、評估日期），衰減是顯示時即時計算的。

### 標籤篩選

工具列下方是一排標籤按鈕，**選起來的標籤才顯示**：

- **一個都沒選** ＝ 顯示全部（預設狀態）。
- **選了標籤** ＝ 只顯示帶有其中**任一**標籤的人（多選是「或」），沒有標籤的人這時就不會出現。選了之後右邊出現「清除選取」。

**名單卡與趨勢分析共用這一排**——調整之後卡片與圖表會一起重算。選擇會**依帳號記在這台裝置上**（localStorage，key 帶 uid，共用電腦不會互相蓋掉）。

這只是畫面顯示層級的過濾，**AI 建議仍會看到完整名單**以做出更好的判斷。但「AI 評估熱度」、趨勢分析的統計與匯出的 CSV 都只涵蓋目前顯示的人——所以要**只匯出某些標籤的名單**，選好標籤再按匯出就好。

每個人有兩份獨立的紀錄，透過卡片上的按鈕開啟，與新增/編輯名單的表單分開管理：

- **活動紀錄**（活動名稱、日期、反應）：參加過哪些活動、當下的反應。
- **聯絡紀錄**（日期、內容）：每次聯絡（聊天、通話、見面等）的日期與談了什麼。

兩份紀錄都**依日期新到舊排序**（最新的在最上面；沒填日期的排最後，新增時日期預設為今天）。日期欄位為日曆選擇器，反應／內容為多行輸入框。卡片上直接顯示**最近 2 筆**、其餘以「還有 N 筆…」帶過，完整歷程點卡片上的按鈕開紀錄視窗查看。兩份紀錄都會在產生 AI 建議時一併送給 AI 參考。

## 班務系統

切到「班務系統」分頁之後是一套獨立的畫面：工具列（搜尋、班別、班員／護班人員、課程管理、＋新增名單）與班務名單卡。

### 名單

每一筆班務名單有：姓名、**班別＋身分**（可以有好幾組）、性別、系級、備註，以及**關聯的道務名單**。欄位跟道務名單不一樣，但**版面樣式與道務的新增名單相同**（同一組表單 CSS）。

#### 一個人可以同時在好幾個班

班別（新民／至善／行德／崇德／人才儲訓／講培／講師）與身分（班員／護班人員）是**成對**的，一筆名單可以有好幾對——例如「新民・班員」再加「至善・護班人員」。編輯視窗裡按「＋ 再加一個班別」加一組，同一個班只會留一組。卡片上每一組都是一個標籤。

因此**工具列選某個班別，該班的班員與護班人員都會列出來**（也就是那個班的完整名冊）；再搭配「只看班員／只看護班人員」就會縮到同一組裡符合的人。用班別篩選時，卡片上符合的那個標籤會被框起來。

> 資料上存成 `roles: [{ group, type }]`，同時把第一組也寫進舊的 `classGroup`／`memberType` 欄位。舊資料（只有 `classGroup`／`memberType`）讀進來會自動當成一組角色，不用轉檔。

#### 打姓名就自動關聯

新增／編輯時在**姓名**欄打字，若道務名單裡有同名的人會即時列出來，選一位就把兩邊接起來，同時**自動帶入他的性別與系級**（只在該欄還空著時才帶，已經填的不會被蓋掉）。關聯的對象顯示在編輯視窗裡（卡片上不重複顯示一次），關聯錯了可以按「取消對應」。

名單本身**不共用**——同一個人在兩個系統各有一筆資料、各記各的東西——關聯只是讓你知道這兩筆是同一個人。也可以完全不關聯（例如還沒進到道務名單的新班員），直接把姓名打完就好。

姓名比對的來源是道務的姓名索引 `rosterIndex`（含姓名、系級、性別），所以**不受道務的身分階梯限制**，找得到單位裡的每一個人。

#### 性別與系級兩邊同步

關聯起來之後，**性別與系級是同一份資料：哪一邊改，另一邊就跟著改**。

- 改道務名單 → 存檔時同步寫進所有關聯到他的班務名單。
- 改班務名單 → 存檔時寫回道務名單那一筆與姓名索引。
- 對方沒有另一個系統的權限而寫不進去時：班務改道務會直接跳訊息說「道務那邊沒同步到」；道務改班務則靜靜略過，之後班務名單載入時會自己從姓名索引補上（每一筆記著上次對齊的樣子 `daoProfile`，所以只有「道務那邊真的改過」才會覆蓋，班務自己剛改還沒推回去的內容不會被蓋掉）。

其他欄位（備註、班別、上課紀錄…）各記各的，不會互相影響。

### 上課紀錄

卡片上的「**上課紀錄**」按鈕開啟紀錄視窗，欄位**依身分而不同**：

| | 班員 | 護班人員 |
|---|---|---|
| 共同 | 課程、出席狀況（準時／遲到／請假／缺席）、備註 | 同左 |
| 專屬 | **有寫筆記**、**課堂有提問** | **與班員互動狀況**、**學習項目**（例：準備點心、課後整理） |

**紀錄從課程長出來，不用再填日期**：先挑一堂課，日期就跟著那堂課帶入，**班別與身分也一起決定**（課程屬於哪一班，他在那一班是班員就記學習狀況、是護班人員就記承擔狀況，畫面上會寫「2026-08-10・以『新民・班員』紀錄」）。所以紀錄一定要對到一堂課；那堂課還沒登錄的話，先到「課程管理」新增。

**只列得出他自己那幾班的課**：新民班的班員不會看到至善班的課。同時在好幾個班的人，兩邊的課都列得出來，挑哪一堂就算哪一班。

**而且只列還沒記過的課**：記過的那幾堂會從清單消失（舊紀錄沒有課程 ID 的，用課名＋日期比對），所以不會同一堂課記兩次；都記完了就顯示「他那幾班的課都記過了」。要改已經記過的內容，直接改下面那幾筆。

紀錄依日期新到舊排列，列上會標出佛堂與課程名稱；卡片上會顯示最近一筆的摘要（例如「2026-08-09・新民班第三堂・準時・有筆記・有提問」）。

### 佛規禮節與經典背誦

上課紀錄之外，每一位還有兩本自己的簿子，卡片上各一個按鈕：

| | 佛規禮節 | 經典背誦 |
|---|---|---|
| 記什麼 | 哪一天、**什麼事情**、**學習項目** | 哪一天、**背了哪一部經典** |
| 例子 | 2026-08-01・初一獻供・上執禮 | 2026-08-05・彌勒救苦真經 |
| 共同 | 備註（選填），最新的排最上面，可以逐筆刪除 | 同左 |

這兩種**跟課程無關**（佛規禮節常常發生在獻供、法會這類場合，不是上課），所以日期自己填，預設今天。

**用過的詞會列出來給你點**：全單位登錄過的「學習項目」與「經典」會排在輸入框下面，點一下就填進去——同一件事才不會被打成好幾種寫法（上執禮／執禮／上執禮生…），日後要統計也才對得起來。

卡片上的計數顯示成「上課 N・佛規 N・背誦 N」，一眼看得出誰的哪一塊還是空的。刪除名單時會列出這三種紀錄各有幾筆再問一次。

資料存在名單文件的 `etiquette` 與 `recitations` 兩個陣列裡（`{ date, occasion, items, comment }` 與 `{ date, scripture, comment }`），跟上課紀錄一樣是名單的一部分，不另外開集合。

### 課程管理

「課程管理」是班務版的活動管理，一堂課有**佛堂、班別、日期、課程名稱**。

**為什麼要填佛堂**：同一個班別在不同佛堂各自開課——「崇慧新民」是崇慧佛院的新民班，跟崇德佛堂的新民班是兩回事。課程清單就按 **佛堂＋班別**分組，每一組可以**收合**（標題列出幾堂課與最近的日期），佛堂多的時候才不會整頁都是課。組內**依日期由舊到新**排，跟實際上課的順序一致。已經用過的佛堂會列在輸入框下面，點一下就填進去。

**新增與儲存是兩個按鈕**：平常只有「新增課程」；按了某一堂的「編輯」之後才會換成「儲存變更」與「取消編輯」，那一列也會標成正在編輯，不會按錯把新課程存成修改。新增完成後佛堂與班別會留著，方便接著登錄同一班的下一堂。

刪除課程不會動到已經寫進個人上課紀錄的內容（紀錄裡存了當時的佛堂、課名與日期）。

### 身分（班務組長）

班務系統的身分存在 `memberEmails/{gmail}.classRank`，跟道務的 `roleRank` **分開**：

| classRank | 身分 | 說明 |
|---|---|---|
| 4 | 點傳師 | 與道務共通，依 `roleRank` 自動帶入 |
| 3 | 忠義字班講師 | 與道務共通，依 `roleRank` 自動帶入 |
| 2 | 班務組長 | **只在班務系統**，要另外設定 |
| 1 | 班務人員 | |
| 0（或沒寫） | **未授權** | 進不了班務系統 |

**「成全組長」不等於「班務組長」，「組員」也不等於「班務人員」**——道務的身分不會自動變成班務的身分，反之亦然；只有點傳師與忠義字班講師（3、4）兩邊共通，設一次就好。

因此**一邊有身分、另一邊是「未授權」的帳號，就只能用有身分的那一邊**：

- 另一邊的分頁會標成「班務系統（未授權）」，點下去跳出「你沒有班務系統的權限，請聯絡管理員在『使用者管理』裡指定班務身分。」，畫面不會切過去。
- 這不只是畫面上藏起來：安全規則裡 `entries`／`personalEntries`／`events`／`chatHistories` 要 `roleRank ≥ 1`，`classEntries`／`courses` 要 `classRank ≥ 1`，**沒授權的那一邊連讀都讀不到**。
- 兩邊都是 0 的帳號**登入就會被擋下來**（提示這個帳號還沒被授權任何系統）。

在「使用者管理」裡每個帳號有兩個下拉：道務身分與班務身分，兩個都可以選到「未授權」（也就是把某人的某一邊關掉）；新增帳號時兩個都選未授權會被擋下來。班務組長以上一樣看得到「使用者管理」。

> 班務名單**沒有道務那種身分階梯**：同單位的人共同維護班務名單與課程，彼此都看得到。班員的學習紀錄不像成全紀錄那樣需要分層保護，若之後要加再說。

## 趨勢分析

工具列的「**趨勢分析**」按鈕會在**工具列與名單卡之間**展開一區（不是彈出視窗、也不換頁，名單卡一直都在下面；按鈕變成「收起趨勢分析」），內容是四張堆疊長條圖：**道氣／成全熱度／互動度／參與度**。y 軸是人數，每根長條由下往上依序堆「弱（無、冷）→ 普（低、涼）→ 佳（中、溫）→ 強（高、熱）」，所以整根的高度就是總人數，一眼看得出**組成怎麼變**。

四張圖在**寬螢幕會排成兩欄**（每欄至少 420px），窄螢幕自動收成一欄，圖表才不會被拉得又寬又扁。

左上角的時間選單決定**看多久**以及**一格代表多久**：

| 選項 | 看多久 | 一格 | 幾格 |
|---|---|---|---|
| 近一週 | 前七天到今天 | 一天 | 7 |
| 近一月 | 最近四週 | 一週 | 4 |
| 近一年 | 最近十二個月 | 一個月 | 12 |

**一格＝那一段期間內發生的事**，不是某一天的快照；最後一格只算到今天為止。所以「近一月」的「8/4」那根長條指的是 8/4–8/10 這一整週，點下去的篩選提示會顯示實際起訖。

各指標在一格之內的算法：

- **互動度**：期間內有互動的天數 ÷ 期間天數，門檻沿用卡片上的規則（≥2/7 高、≥1/7 中、有就是低）。用比例，一天／一週／一個月的格子才是同一把尺。
- **參與度**：期間內辦過的活動裡出席了幾成（≥60% 高、≥30% 中、>0 低），期間內沒活動就是「—」。
- **成全熱度**：它是「當下的狀態」而不是累積量，所以取**期間結束那天**的值。
- **道氣**：用上面三個期間值合成。

### 道氣

把三個指標合成一個總分，衡量整體氣氛：

```
道氣 ＝ 熱度 × 0.6 ＋ 參與度 × 0.2 ＋ 互動度 × 0.2
```

每個指標都是 0–3 級，換算成 **0–100 分**：73 分以上＝**強**、47 分以上＝**佳**、1 分以上＝**普**、0 分＝**弱**。熱度佔六成，因為「談到哪裡」最能代表成全的深度；參與度與互動度各兩成，補上「有沒有實際往來」。道氣圖的右上角另外顯示**目前全體的平均分數**。

### 指標怎麼回推

四個指標本來就是從活動紀錄與聯絡紀錄推算出來的，這裡只是把「今天」換成過去某一天再算一次，**不另外儲存歷史資料**——所以補登舊紀錄之後，過去的趨勢也會跟著修正。唯一的例外是熱度的基準值（AI 或手動評的）只有現在這一版，因此回推時的規則是：**那一天之前如果還沒有任何紀錄，就算成「冷」**，不會把之後才評出來的熱度套到更早以前。

統計範圍跟名單卡完全一致，工具列上的篩選全部吃得到：**標籤篩選**、**成全狀況**、**全部／團隊／我的個人名單**，以及**檢視身分**。切換任何一個，圖表與名單卡都會即時重算（換檢視身分時會重新訂閱名單，資料一回來圖表就跟著換成新的那批人，圖表篩選也會先清掉）；匯出的 CSV 同樣跟著這個範圍。

### 點圖＝篩選名單卡

點圖上的任何色塊（或下方圖例的「弱／普／佳／強」「冷／涼／溫／熱」「無／低／中／高」）就會**把下面的名單卡篩成那一群人**——所以「那個分類的名單」長得就跟平常的名單卡一模一樣，該有的按鈕（活動紀錄、聯絡紀錄、熱度、編輯…）都在。圖例點下去看的是最新一期。

**圖例會解釋每一級是什麼意思**：圖例下面逐條列出（例如「熱＝聊到下一階段且對方正面回應」「強＝73 分以上：熱度與出席都好」「高＝平均每週兩天以上」），滑鼠移到圖例上也看得到同一句。光寫「熱」「強」沒人猜得出標準；說明直接寫在畫面上而不是只放 title，是因為手機沒有 hover。單人趨勢的四條線同樣在下面列出各級定義，滑到線的名稱上還會顯示完整算法。

圖表下方會出現一條「只顯示：道氣「強」· 日期 · N 人」的提示，按「清除篩選」或收起趨勢分析就回到完整名單。

### 單人趨勢

名單卡上的「**趨勢**」按鈕會在趨勢區塊裡畫出那個人自己的四條線：道氣、熱度、互動度、參與度。刻度是 0–3 級，道氣是 0–100 分等比例縮到同一把尺上，所以四條線可以直接互相比較；下面另外標出他現在的四個數值。

這張圖有**自己的時間選單**（在標題左邊，同樣是近一週／近一月／近一年），可以跟上面的整體圖表看不同尺度。

- **兩個 y 軸**：左邊是 0–3 級（熱度、互動度、參與度），右邊是 0–100 分（道氣，紫色），兩把尺分開標示，不會互相混淆。
- **滑到點上**會顯示那一格的實際值（例如「8/6 熱度 溫」「8/6 道氣 67 分」）。
- **日期上方的 📝**表示那一格有紀錄，**點下去**會在圖表下方展開內容（🎪 活動＋反應、💬 聯絡＋談了什麼）。圖示畫在日期文字上方一層，不會互相蓋到；圖示周圍有一塊看不見的觸控範圍（手機上約 42×43px），手指也點得準。
- 手機上整張圖會改用比較窄的畫布重畫，文字與圖示不會被整體縮小到看不清楚（轉向時會自動重算）。
- 電腦上圖**最寬只到畫布本身的 720px**（連同圖例與展開的紀錄一起收齊）。不設上限的話，寬螢幕會把整張圖放大到近兩倍，文字與圓點跟著變粗；手機仍然是滿版。

### 匯出 CSV（一列就是一條走勢）

趨勢區塊上方的「**匯出 CSV**」匯出的是**橫向的時間序列**：

| 姓名 | 系級 | 歸屬 | 成全狀況 | 標籤 | 指標 | 5/23 | 5/30 | … | 8/1 | 8/8 |
|---|---|---|---|---|---|---|---|---|---|---|
| 甲同學 | 資工三 | 團隊名單 | | 需關心 | 道氣分數 | 0 | 0 | … | 100 | 100 |
| 甲同學 | 資工三 | 團隊名單 | | 需關心 | 道氣 | 弱 | 弱 | … | 強 | 強 |
| 甲同學 | 資工三 | 團隊名單 | | 需關心 | 成全熱度 | 冷 | 冷 | … | 熱 | 熱 |
| 甲同學 | 資工三 | 團隊名單 | | 需關心 | 參與度 | 無 | 無 | … | 高 | 高 |
| 甲同學 | 資工三 | 團隊名單 | | 需關心 | 互動度 | 無 | 無 | … | 高 | 高 |

**一個人八列（每個指標一列），欄位就是各個期間**，所以一列橫著讀就是那個人的趨勢——哪一格是「涼」、哪一格轉「熱」直接看得出來，也可以整列拉去畫折線圖。指標包含：道氣分數、道氣、成全熱度、參與度、互動度，加上**期間內互動天數／活動紀錄／聯絡紀錄**三個原始數字，方便自己驗算。

期間跟畫面上選的一致（近一週＝7 個單日欄、近一月＝4 個單週欄、近一年＝12 個單月欄），每一格都是**那一段期間內**算出來的。檔案第一列另外標出每段期間的實際起訖（例如 `2026/8/4–2026/8/10`），不會只看到「8/4」不知道涵蓋到哪。

匯出範圍就是目前畫面上看得到的那批人（標籤、成全狀況、團隊／個人名單、檢視身分都算），檔名會帶上主要條件，例如 `名單趨勢_台科崇德_團隊名單_需關心_月_2026-08-10.csv`。**檔案含真實姓名，請比照名單本身保管。**

檔名是 `名單分析_單位名稱_日期.csv`，內容為 UTF-8 並附 BOM，用 Excel 直接開不會變亂碼。**檔案含真實姓名，請比照名單本身保管。**

## 近兩週活動提醒

登入後，如果**未來 14 天內**有登錄的活動，名單上方會出現提醒橫幅，逐筆列出：還有幾天、活動名稱與類型，以及目前的邀約狀況（已邀約幾人、幾人回覆可以、幾人待確認；**還沒邀約任何人的會用紅字標示**）。

點該筆的「**安排邀約**」會直接開啟活動管理並跳到那個活動的編輯畫面，下面就是邀約看板與「AI 建議邀約」，可以馬上決定邀誰。

右上角的「今天不再顯示」會把橫幅收起來，隔天會自動再出現（記在瀏覽器的 localStorage，只影響自己這台裝置）。

## 活動結束後回報參與狀況

活動辦完了卻沒人回報誰有來，參與度與道氣就會一直是舊的。所以**活動結束後（60 天內）還沒回報完的**，名單上方會出現琥珀色的提醒橫幅，列出活動名稱、幾天前結束，以及**「要回報 N 人・已回報 X 人・還缺 Y 人」**（N 是真正要回報的人數，不含下面兩種免回報的人）。

點「**回報參與狀況**」開啟回報視窗：

- **只列出「已回覆可以」的人**（會不會來本來就只有他們要確認），而且**不列出你自己**——自己有沒有到不用自己回報。
- **忠義字班講師以上（含點傳師）完全不用回報**，連人數都不算進去。活動紀錄是給成全對象用的，講師本來就是辦活動的人；把他們列進來只會讓提醒永遠關不掉（沒有人的身分比點傳師高，那一列誰都填不動）。
- **一位一位回報**：每個人一列，姓名、「**有參加／沒參加**」選單、兩行備註欄，以及那一列自己的「**回報**」按鈕。填好一個就送一個，不用等全部填完，也不會因為某一位卡住而整批失敗。
- **有參加**：備註寫他的反應 → 寫進他的「**活動紀錄**」（活動名稱與日期取自這場活動），參與度與道氣立刻跟著更新。
- **沒參加**：備註寫沒來的原因 → 寫進他的「**聯絡紀錄**」，內容是 `未參加「活動名稱」：原因`。**刻意不寫成活動紀錄**，否則參與度會把沒來的人算成有出席。沒填原因就什麼都不寫。
- **已經有同一場、同一天紀錄的人會自動略過**，重複回報不會產生重複紀錄。
- 已經有人回報過的那一列會顯示結果與回報人，要改按「**重新回報**」。
- **同一階或更高的人顯示「請學長姐填寫」**：他們的名單你本來就改不動（安全規則也擋著），所以不給你填，要由身分比他高的人回報。

### 提醒什麼時候才會消失

**除非要回報的每一位都回報過了，或有人按了「回報完成」，提醒會一直留在頁面上**，並且顯示還缺幾位——這樣才不會有人以為別人回報過了就放著不管。

每一位的回報結果記在活動的 `reports` 欄位（`{ entryId: { came, note, by, at } }`），最後一位回報完才會把活動標成 `attendanceReported`。狀態存在活動本身，所以是**整個單位共用**的：別人回報過的人，你打開就看得到，兩個人同時開著視窗也會即時同步（你正在打、還沒送出的內容不會被蓋掉）。

「**回報完成**」是收尾用的按鈕：不必等每一位都回報，按下去就**結束這一場**、提醒對所有人消失。按之前會先確認，並告訴你還有幾位沒回報；已回報「有參加」的人仍算進出席名單，之後還是可以到活動管理裡手動補紀錄。剩下的人如果只有學長姐才填得動、又遲遲沒人填，就用這個結掉。

## 活動管理

工具列的「**活動管理**」按鈕開啟**月曆檢視**（一週一列、活動落在對應日期格，多日活動每一天都會出現）。可上一月／下一月／今天切換。點空白日期格會把該天帶入下方表單的開始日期，點月曆上的活動則載入表單編輯或刪除。**編輯到一半再點空白日期格，會自動退回「新增活動」模式**（帶入你點的那天），不會讓你以為在開新活動、其實還在改舊的那一筆。月曆會補滿完整週，**當月前後鄰月的日期與活動也會以淺字顯示**，方便銜接看。

單日活動只需要選一個日期；勾選「**多日活動**」才會出現第二個日期選擇（結束日期），不用每次都面對兩個日期欄位。

### 邀約名單

點月曆上的活動進入編輯後，下方會出現該活動的**邀約名單**，做成五個狀態框：**預定邀約／已邀約待回覆／回覆不確定／已回覆可以／已回覆不行**，各框顯示人數，上方也有整體摘要。

- **加入**：在輸入框**打字搜尋**（可搜姓名、系級、背景），下方會即時列出符合且還沒加入的人，點一下就加入；也可以選好狀態按「加入」或按 Enter。輸入的名字若有多位符合，會請你從清單點選，避免加錯人。
  - **邀約不受身分階梯限制**：這裡搜得到、也顯示得出**全單位每一位**的名字（名字取自 `rosterIndex`），因為要邀約當然得找得到人。看不到的只是對方名單卡上的內容（成全狀況、背景、紀錄），那部分仍受階梯保護。
- **改狀態與備註都在下方的編輯區**：點名字打開它，裡面有備註欄與**狀態**下拉，按「儲存備註與狀態」一次寫進去。這兩件事幾乎總是一起發生（「他說可以來」＝記一句備註＋改成已回覆可以），而且**iOS 上的瀏覽器（Safari、Firefox…）沒有 HTML5 拖放**，所以 iPhone 也得從這裡改狀態。看板上的卡片維持乾淨，只有名字與備註。
- 電腦上另外可以直接把名字**拖到另一個框**改狀態。
- **移除**：點名字旁的 ×。
- **AI 建議邀約**：**按下後會先跳出確認**（告訴你會從幾位裡挑、目前已邀約幾位、資料會去識別化後送給 AI、要跑一陣子），確定後 AI 才會依活動類型與每個人的成全狀況、背景、活動與聯絡紀錄，挑出適合邀約的人**自動加進「預定邀約」**，並附上一句話理由。它只會從「還沒加入名單」且**你看得到**的人裡挑，而且被要求寧缺勿濫——沒有合適的人就會直說。

所有變更都**立即存回資料庫**（存在該活動文件的 `invites` 欄位，記錄的是對象 ID，所以之後改名字也不會對不上）。

邀約狀況（含備註）也會送給 AI 參考：已回覆不行的活動不會再推薦給同一個人，已回覆可以的則會著重後續陪同，回覆不確定或待回覆的會建議如何再確認、化解對方的顧慮；聊天室助手也能回答「誰還沒回覆某活動」。每筆活動包含：開始日期、結束日期（選填，留空表示單日活動，例如兩天一夜的幹訓）、名稱、類型（**廣結善緣／獻供／求道／成全／法會／幹訓／會議**，不同類型以不同顏色標示；**會議**是團隊內部開會，AI 不會把它推薦給成全對象），存在 `units/{unitId}/events`，同單位成員都能維護。

AI 產生建議時會參照今天（含）以後的活動：單一對象建議會多產出「**推薦活動**」（依對象狀況挑選——接觸初期或反應冷淡者推廣結善緣，時機成熟的未求道者推求道，已求道者推成全求道或法會，較資深、有心承擔者推幹訓），套用後顯示在卡片上；聊天室助手也能回答「誰適合參加哪個活動、怎麼鋪陳邀約」。這項「幫對象挑合適的活動」正是靠 AI 判斷對象狀況與活動類型的搭配，不是寫死的規則。

## 去識別化（僅用於 AI 分析）

系統內的顯示與資料庫儲存都保留**完整姓名**；只有在把資料送給 AI 分析時，**姓名、聯絡人**才會換成中性代號：王小明 → 代號3、張三 → 代號7。代號完全看不出是誰（不像遮罩還留著姓氏與字數），保護力更強。

這是一份**可還原的對照表**：AI 依代號回覆後，系統會自動把代號換回真名再顯示（例如 AI 說「建議代號3參加法會」，你看到的是「建議王小明參加法會」）。Anthropic 收到的資料完全不含真名。

### 自由文字欄位裡的名字也會處理

背景、策略、做法、活動紀錄、聯絡紀錄、活動名稱這些自由文字裡若提到名單上的人（不論是成全對象或聯絡人），送出前一樣會換成代號。為了讓實際寫法也能被抓到，對照表額外涵蓋：

- **簡稱**：名單登記「王小明」，背景寫「小明介紹的」→ 一樣換成同一個代號（三個字以上的姓名才推導簡稱；兩個字的名字去掉姓只剩一個字，會誤蓋到一般用字，所以不推）。
- **一格多人**：聯絡人欄寫「張三、李四」時，整串與拆開的「張三」「李四」都各自建立對應，背景只提到其中一位也會被換掉。

自行留意：只有**名單上登記過的姓名/聯絡人**會被代換。若你寫了名單外的人名，或學校、單位全名，不會自動處理，請自行斟酌。

## AI 成全建議（Claude）

AI 功能使用 **Claude Opus 4.8**（Anthropic 最強的 Opus 模型，擅長細膩的成全建議），有兩種使用方式：

### 1. 單一對象建議

卡片上的「AI 建議」按鈕：開啟視窗後可以（選填）輸入**一句話的策略方向**（預設帶入該對象目前的策略），AI 會依你的方向與該對象去識別化後的背景、成全狀況、活動紀錄、聯絡紀錄，加上近期活動清單，產生「策略」「具體做法」與「推薦活動」，滿意的話一鍵套用回欄位（套用時已換回真名）。

### 2. AI 成全助手（聊天室）

登入後右下角有藍色「AI」浮動按鈕，點開是一個聊天視窗。這位助手**能看到整份名單**（每一位的姓名、聯絡人都以代號呈現），可以自由對話詢問，例如：

- 「哪幾位適合邀約下個月的法會？」
- 「王小明最近反應冷淡，接下來怎麼做比較好？」（你打的真名送出前會換成代號）
- 「幫我排一下這份名單的成全優先順序。」

畫面上的對話一律顯示真名（AI 內部用代號，回覆後自動轉回）。

**對話會自動保存**：存在 `units/{unitId}/chatHistories/{你的 uid}`，每位使用者一份，安全規則限定**只有本人讀得到**（同單位的其他成員也看不到你的對話）。重新整理、關掉瀏覽器或換裝置登入，紀錄都還在。按「清除對話」會一併把雲端那份清空。

### 設定共用 API Key（管理員做一次）

所有已授權帳號共用一把 Anthropic API Key，存在 **Firestore 的 `config/ai` 文件**，由安全規則保護——只有設定過歸屬單位的帳號讀得到，使用者不需要各自輸入。

1. 到 [console.anthropic.com](https://console.anthropic.com/) 註冊、儲值並建立 API Key。
2. 到 Firebase Console →「Firestore Database」→「資料」→ 新增集合：
   - 集合 ID：`config`
   - 文件 ID：`ai`
   - 欄位：`anthropicApiKey`（字串），值填入你的 API Key
3. 確認 Firestore 規則已更新為本專案最新的 [firestore.rules](firestore.rules)（含 `config` 集合的讀取限制）並發布。

> ⚠️ **不要**把 API Key 放進 `.env`、GitHub Secrets 或任何會被 build 進前端的變數——`VITE_*` 環境變數會直接寫進部署後的公開 JS 檔，任何人不用登入就能取走這把 Key。存在 Firestore 由安全規則保護，是純前端架構下唯一不會公開 Key 的做法（Firebase 那組設定值可公開，性質不同）。
>
> 換 Key 或停用：直接到 Firebase Console 修改/刪除 `config/ai` 文件即可，不用重新部署（使用者重新整理頁面後生效）。

## 一、建立 Firebase 專案（一次性設定）

1. 到 [Firebase Console](https://console.firebase.google.com/) 建立新專案。
2. 左側選單「Authentication」→「Sign-in method」→ 啟用 **Google** 這個登入方式。
3. 左側選單「Firestore Database」→「建立資料庫」→ 選正式環境模式、選一個離你近的地區（如 asia-east1）。
4. Firestore 建好後，到「規則(Rules)」分頁，把內容換成本專案的 [firestore.rules](firestore.rules)，然後發布。
   （授權帳號的方式見下方第二節）
5. 左側選單「專案設定」→「一般」→ 拉到最下面「你的應用程式」→ 新增一個「網頁」應用程式 → 複製產生的 `firebaseConfig` 物件。
6. 設定值**不寫在原始碼裡**，改用環境變數（見下方「設定 Firebase 金鑰」）。
7. **授權網域**：部署到 GitHub Pages 後，回到「Authentication」→「Settings」→「Authorized domains」，把你的 Pages 網域（例如 `ntustcdvc1979.github.io`）加進去，Google 登入彈窗才不會被擋。

### 設定 Firebase 金鑰（環境變數）

`firebaseConfig` 的值改由環境變數提供，程式碼裡不再寫死（[src/firebase.js](src/firebase.js) 讀 `import.meta.env.VITE_FIREBASE_*`）。

**本機開發**：複製 [.env.example](.env.example) 為 `.env.local`，填入你的實際值。`.env.local` 已被 git 忽略，不會上傳。

```bash
cp .env.example .env.local   # 然後編輯 .env.local 填入實際值
```

**GitHub 部署**：到 repo → Settings → Secrets and variables → Actions → New repository secret，逐一新增下面 6 個 secret（名稱要一模一樣）：

| Secret 名稱 | 值 |
| --- | --- |
| `VITE_FIREBASE_API_KEY` | apiKey |
| `VITE_FIREBASE_AUTH_DOMAIN` | authDomain |
| `VITE_FIREBASE_PROJECT_ID` | projectId |
| `VITE_FIREBASE_STORAGE_BUCKET` | storageBucket |
| `VITE_FIREBASE_MESSAGING_SENDER_ID` | messagingSenderId |
| `VITE_FIREBASE_APP_ID` | appId |

GitHub Actions build 時會自動把這些 secret 注入（見 [.github/workflows/deploy.yml](.github/workflows/deploy.yml)）。

> ⚠️ 注意：Firebase 的 Web `apiKey` **不是密碼**，它最終仍會出現在部署後的前端 JS 中，任何人都看得到，這是靜態網站的正常情況。用環境變數只是讓「原始碼乾淨、不觸發 GitHub 掃描警告」。真正的存取防護請看下面的「安全性」一節。

## 二、授權帳號（重要！）

本系統用 **Google 帳號登入**。Google 登入預設會讓**任何一個 Google 帳號都能通過驗證**，所以「誰能看到資料」是另外由帳號歸屬決定——**沒有被指派道務單位的帳號，登入後會立刻被登出，什麼都讀不到**。

授權方式只有一種：把對方的 Gmail 寫進 `memberEmails`。只要知道 Gmail 就能先設好，不用等他登入過：

1. Firebase Console →「Firestore Database」→「資料」，在 **`memberEmails`** 集合建立文件：
   - 文件 ID：他的 Gmail，**全部小寫**（例如 `someone@gmail.com`）
   - 欄位：`unitId`（字串）＝ 他所屬的道務單位 ID
2. 若那個單位還不存在，在 **`units`** 集合建立文件：
   - 文件 ID：單位 ID（例如 `ntust-chongde`）
   - 欄位：`name`（字串）＝ 顯示用的單位名稱（例如「台科崇德」）
3. 請他用**同一個 Gmail** 登入即可。

> 文件 ID 必須跟他 Google 帳號的 Email 完全一樣。Google 帳號的 Email 一律是小寫，所以請用小寫；打錯不會有錯誤訊息，只會一直進不去。

### 身分與可見範圍

每支帳號有一個**身分**，寫在 `memberEmails/{gmail}.roleRank`：

| roleRank | 身分 | 看得到 |
|---|---|---|
| 4 | 點傳師 | 忠義字班講師、成全組長、組員、非組員 |
| 3 | 忠義字班講師 | 成全組長、組員、非組員 |
| 2 | 成全組長 | 組員、非組員 |
| 1 | 組員 | 非組員 |
| 0（或沒寫） | **未授權**（帳號）／非組員（名單上的一筆） | — |

帳號的 `roleRank` **沒寫就是 0＝未授權，進不了道務系統**（要另有 `classRank ≥ 1` 才能用班務系統）。名單每一筆的 `roleRank` 沒寫則是 0＝非組員（一般成全對象）。

規則是**只看得到比自己更低階的人**，所以**同一階之間互相看不到**（講師看不到其他講師、組長看不到其他組長）。名單每一筆也有 `roleRank`（沒有就是 0＝非組員），由**忠義字班講師以上**在名單編輯裡設定。

**檢視身分**：組長以上的人，工具列會多一個下拉可以切換模式——例如講師切到「成全組長模式」就只看得到組員與非組員，切到「組員模式」就只剩非組員。切換只能往下，不能超過自己的身分。

**這是資料庫層級的管制**：安全規則要求查詢條件必須是 `roleRank < 自己的身分`，看不到的資料連讀都讀不到，不是只在畫面上藏起來。

### 使用者管理（成全組長以上）

**成全組長以上**（組長、忠義字班講師、點傳師）看得到工具列的「使用者管理」，也只有他們改得動 `memberEmails`：

每個帳號是一張卡片：頭像（依 Email 固定配色）、Email、綁定到名單上的誰，下面一排是道務／班務兩個身分與綁定按鈕，右上角的 ✕ 是移除。帳號多的時候可以用上面的搜尋框找 Email 或綁定的姓名，旁邊顯示「幾／幾人」。

- **加入**：填對方的 Gmail、選道務身分與班務身分按「加入」（兩個都選「未授權」會被擋，那樣他哪一邊都進不去）。
- **改身分**：每張卡片兩個下拉——道務身分、班務身分，各自都可以設成「未授權」把那一邊關掉；**兩邊都設成未授權會先跳出確認**（等於把人擋在門外）。自己的身分不能改，顯示成灰色標籤。
- **指定綁定**：指定那個帳號是名單上的誰（見上面「帳號綁定」）。
- **移除**：會先跳出確認（含對方目前的身分），確定後他下次就登不進來。名單資料不受影響，把同一個 Gmail 加回來即可恢復。

可以指派到哪一階（規則層擋著，不只是畫面）：

| 你的身分 | 可以把別人設成 |
|---|---|
| 點傳師（4） | 組員～點傳師 |
| 忠義字班講師（3） | 組員～**點傳師** |
| 成全組長（2） | 組員、成全組長 |

也就是**組長只能設到自己這一階以下，但講師以上可以一路指派到點傳師**（講師要能把點傳師請進系統）。不論哪一階，**都不能改自己的身分**（避免自我升等），也碰不到別的單位。第一位講師／點傳師請在 Console 直接把 `memberEmails/{gmail}.roleRank` 設成 `3` 或 `4`。

**名單每一筆的身分**（名單編輯裡的「身分」欄位）另外算，仍然只有**忠義字班講師以上**改得動。

### 綁定自己不受身分階梯限制（`memberLinks` vs `rosterIndex`）

兩份資料**不是重複綁定**，各做各的事：

| 集合 | 內容 | 做什麼 |
|---|---|---|
| `memberLinks/{uid}` | `{ entryId }` | **綁定結果**：這支帳號對應名單上的哪一筆。一個帳號一份，只有本人寫得動。 |
| `rosterIndex/{entryId}` | `{ name, department, gender, roleRank }` | **姓名索引**：讓你在還沒綁定之前，搜尋得到自己的名字；班務系統也靠它把姓名對應到道務的同一位（帶入性別、系級）。 |

為什麼不能只用 `memberLinks`：它只記「已經綁好的人綁到哪一筆」，**沒有姓名**，而且**還沒綁的人根本不在裡面**。第一次綁定時你要用名字搜尋自己那一筆——但自己那一筆通常跟自己同階，被身分階梯擋住、連讀都讀不到，搜尋當然找不到。所以另外放一份只有**姓名、系級、性別、身分**的索引，同單位每個人都讀得到（**含只有班務權限的帳號**，班務新增名單時要靠它比對姓名）；成全狀況、背景、紀錄那些內容仍然受身分階梯保護。

綁定之後也用得到：工具列要顯示「名字（gmail）」，而你自己那一筆讀不到，名字就是從索引取的。

索引在新增／編輯／刪除／轉為團隊名單時自動同步。**舊資料與任何對不上的地方，由管理員在後台跑補齊腳本處理**（見下一節），使用者端不需要做任何事。

## 後台維護：補齊 roleRank 與姓名索引

`roleRank` 是後來才加的欄位，**舊名單沒有這個欄位就不會被 `roleRank < 檢視身分` 的查詢回傳**（Firestore 對缺欄位的文件根本不比對），所以升級後看不到。同理，索引機制之前建立的名單也沒有 `rosterIndex`，綁定時搜不到。

這件事由 [scripts/backfill-roles.mjs](scripts/backfill-roles.mjs) 一次處理完，用 Firebase Admin SDK 直連 Firestore、**繞過安全規則**，所以能一次補完**所有單位**，不受身分階梯限制。

### 準備（做一次）

1. 取得服務帳戶金鑰（Firebase Console 介面是英文的話，路徑如下）：
   - 左上角專案名稱旁的 **⚙ 齒輪** → **Project settings**
   - 上方分頁選 **Service accounts**
   - 找到 **Firebase Admin SDK** 區塊 → 語言選 **Node.js** → 按 **Generate new private key** → 彈窗再按 **Generate key**
   - 瀏覽器會下載一個像 `taosystem-firebase-adminsdk-xxxxx-1a2b3c.json` 的檔案
2. 把它改名成 `serviceAccount.json`，放在專案根目錄（跟 `package.json` 同一層）。
3. `npm install`

> 找不到 **Generate new private key** 按鈕的話，代表你的 Google 帳號在這個專案不是 Owner／Editor，請專案擁有者操作或先把你升成 Owner。

> 🔴 **那個 JSON 是真正的密鑰**（能讀寫整個資料庫、繞過所有規則）。`.gitignore` 已經擋掉 `serviceAccount*.json` 與 `*-firebase-adminsdk-*.json`，**不要提交、不要外傳、不要放進雲端硬碟共用資料夾**。
>
> 用完想撤銷的話：Google Cloud Console → **IAM & Admin → Service Accounts** → 點那個 `firebase-adminsdk-…` 帳戶 → **KEYS** 分頁 → 刪掉對應的金鑰。之後要用再產生一把新的即可。

### 執行

```bash
npm run backfill -- --dry-run
```

先試跑，只印出「會改什麼」不寫入。確認數字合理後：

```bash
npm run backfill
```

其他參數：`--unit=ntust-chongde` 只處理某個單位、`--key=C:\path\serviceAccount.json` 指定金鑰位置（也吃 `GOOGLE_APPLICATION_CREDENTIALS`）。

腳本會做三件事，並逐單位印出統計：

- 名單缺 `roleRank` 的補成 `0`（非組員）
- 依名單重建 `rosterIndex`（姓名、系級、**性別**、身分對不上的也一併更新）
- 刪掉名單已經不存在、索引卻還留著的孤兒

寫入用 batch（每批 400 筆），可以重複執行，不會重複寫已經正確的資料。

### 什麼時候要跑

- **升級到有 `roleRank` 的版本之後**（一次）。
- **升級到有班務系統的版本之後**（一次）：`rosterIndex` 多了 `gender`，班務新增名單要靠它自動帶入性別。舊索引沒有這個欄位不會壞掉，只是帶不出性別。
- 發布新規則之前或之後都可以——腳本繞過規則，不受影響。
- 之後若發現有人綁定時搜不到自己，再跑一次即可（正常情況下索引是自動同步的）。

### 從 LINE 點連結進來

Google 不允許在 App 的內建瀏覽器裡登入（會出現 `disallowed_useragent`），所以網頁一偵測到是從 LINE 點進來的，就會自動在網址加上 `openExternalBrowser=1` 重新開一次——這是 LINE 支援的參數，會直接跳到手機預設的瀏覽器。

Facebook／Instagram 沒有這種參數：Android 會試著用 `intent://` 交給系統瀏覽器，都不行時網頁上方會出現黃色提示條，教使用者從「⋯」選單用瀏覽器開啟，並附一顆「複製連結」按鈕。

### 移除與換單位

- 移除某人：刪掉他的 `memberEmails/{gmail}` 文件（組長也可以直接在網頁上做）。
- 換單位：改那份文件的 `unitId`。
- **`units` 集合的寫入在安全規則裡一律拒絕**，`memberEmails` 只有該單位的組長改得動，任何人都無法從網頁把自己加進去、升自己當組長或換單位。

## 安全性與隱私

這份名單包含他人的姓名、系級、聯絡方式、以及對他們的「策略/做法」等敏感內容。

### Firebase apiKey 為什麼公開沒關係

Firebase 的 Web `apiKey` 只是用來**識別專案**，不授予任何資料權限，公開在前端是 Google 官方認可的正常做法。因為本專案是純靜態網站，這把 key 一定會出現在部署後的 JS 裡，藏不住也不需要藏。真正的存取控管靠下面三層：

1. **Firestore 安全規則（最重要）**：[firestore.rules](firestore.rules) 以 `memberEmails/{gmail}` 決定帳號歸屬，只有被指派單位的帳號能讀寫該單位的資料，其他人（包含拿到 apiKey 的陌生人）一律被擋。
2. **Google 登入**：必須先用 Google 帳號登入才會有 `request.auth`。
3. **（建議加強）API key 限制**：到 [Google Cloud Console 憑證頁](https://console.cloud.google.com/apis/credentials) → 找到 Firebase 自動建立的 Browser key → 「應用程式限制」設 HTTP 參照網址，只允許 `ntustcdvc1979.github.io/*` 與 `localhost`；「API 限制」只勾用得到的 API。這樣就算別人複製你的 apiKey 也很難從別的網站濫用。
4. **（進階選項）App Check**：若想更嚴格地確保只有你的網站能呼叫 Firebase，可啟用 Firebase App Check（搭配 reCAPTCHA）。

### 帳號管理

- **只幫真正需要的人建立歸屬文件**；要移除某人，把該文件刪掉即可（不用重新發布規則）。
- 用 Gmail 指派時，文件 ID 要跟他 Google 帳號的 Email 完全一致（小寫）；打錯不會報錯，只是進不去。
- 不要把資料截圖或匯出後任意外傳。
